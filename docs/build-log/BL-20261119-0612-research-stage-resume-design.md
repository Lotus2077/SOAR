### BL-20261119-0612-research-stage-resume-design -- 2026-11-19 -- Research stage resume designed: a paused desktop research stage resumes by reusing its settled calls from a reply journal, and sends only the rest

Status: `Proposed`

Scope or hypothesis: Today a research stage that started and did not transfer its packet can never continue. session.ts refuses it as `research_stage_not_replayed`, because no call persists its reply and a restart would reset the role ceilings while keeping the spent calls. BL-20261109-0501-research-stage-pause-design made such a pause end the task incomplete and left resuming to later items. Decision 3 of BL-20261118-0438-desktop-local-research-13a-design has the desktop warn that a pause or quit ends a running stage. Two r3 runs took 36 and 42 minutes (BL-20261118-0606-e0-r3-remeasurement-result). Manus's workflows survive a restart by replaying against a journal of completed calls, and on 2026-11-19 the owner asked this session to take that idea forward. This entry designs the resume and builds nothing. The pull request's description holds the file references.

Decisions:
1. **A reply journal.** When a zero-risk local call of a research reader context settles, the store keeps the reply the stage uses (content, finish reason and usage, never reasoning), the request body's digest and the streaming mode. The entry is keyed by the row and written in the settlement's own transaction. Only a context whose diagnostic retention is `raw` keeps one; every desktop research task is public or synthetic-attested, so it qualifies. This amends the rule that raw research replies are written only in the headless driver's opt-in run directory. The journal never enters a row, event, receipt, export or diagnostics file. It is deleted in the transaction that records the transfer, or when the task ends.
2. **The replay.** A resume of an unfinished stage runs the stage again on the same inputs, card, roles and models. A request whose purpose and body digest match a journaled settled row of the reader context, not yet used in this run, is answered from the journal, in commit order, without a dispatch. The model's checks that follow settlement apply to it as they did the first time. Every other request is sent as today. The stage's logic, ceilings and counts are unchanged, so every reused call counts toward the ceiling it counted toward before, which removes the reason session.ts gives for refusing.
3. **No row is edited.** The `failed` row that a pause leaves stays `failed`, so a pause costs at most K requests of the 200-request pool (K is 1 on the adopted card). The producer counts a `failed` reader row only when no later row of the same context, purpose and packet exists; when one exists, the later row is that call. No completed stage today has a `failed` local reader row, so every producer made today is unchanged. A replay that diverges leaves a settled row unused, and the producer's existing count check refuses the packet.
4. **Still refused, before any dispatch:** a blocking row (`unresolved_dispatch_no_replay`, which the desktop reads as `interrupted_unknown`); a settled reader row without its journal entry, or a streaming mode that differs from the journal's (`research_stage_not_replayed`); an assist or a diagnostics sink, which only headless runs have. A card, configuration or model change stays refused as today.
5. **Admission.** The record is made at the stage's start, budget part included, so the second repairs and the gap rule that read it are unchanged. Only the clock decision moves: it is taken before the first request actually sent, over the work left at that point. A refusal still ends the stage as `research_infeasible_in_clock`, with no stage row. In a fresh run that point is the stage's start, so fresh runs are unchanged. A record decided at a resume says so, and a resume that sends nothing keeps an admitted record. No policy value or pattern moves, so the protocol hash does not move.
6. **Counts.** A resumed run's stage events say how many of their calls, tokens and truncated replies were reused. The verdict receipt, selection.ts and registry-row.py count only what was sent, so nothing is counted twice. The `failed` rows a pause leaves stay in the failed-dispatch count.
7. **The desktop.** The pause and quit-after-waiting offers say that a running stage resumes from its settled calls. The badge and the stage section show the calls reused and sent. Resume is offered for an unfinished stage whose journal is complete, and such a paused task's record reads `paused`.
8. **Left for later, each its own decision.** A crash or "quit now" leaves the in-flight row `committed`, which nothing resolves, so only Cancel is offered. Resolving such a zero-risk local row as `failed` at the next start is a ledger rule, for a later part with a skeptic. The task's 90-minute clock keeps running while the task is paused, so a resume helps only inside that window. Stopping the clock during a pause would change every desktop task, so that is the owner's call.
9. **Parts.** (a) The journal, the replay, the producer rule and the session's resume, behind a session option that nothing sets yet and with its own journal-complete check, so the desktop is unchanged. It is tested on a scripted broker, with a skeptic on the ledger and privacy rules. (b) The desktop sets the option and changes its offers, counts, receipt and view, plus a gated end-to-end case that pauses mid-stage and resumes. Each part gets one light review.
