## Hypothesis

On three fresh synthetic `.docx` files with planted defects, review-2 delivers an
accepted review more often than review-1, at zero fee and with no cloud, search or web
dispatch.

- **The decision it changes** (review row E6, last column): "The desktop review route".
  Review section 5.3 gives the candidates: the edit plan, the host redline applier and
  the fidelity checks, with "two samples with critique and repair if E6 says so".
- **Where the two parts come from.** The loop's design entry
  (BL-20261026-1831-h4-select-and-repair-design) states them as hypotheses:
  - a second local sample recovers a share of local failures;
  - a local critique and a local repair of the chosen draft recover more.
- **What the selection rule can act on.** Selection protocol 2 compares submission, the
  critical checks passed and the deliverables present, in that order, and a tie keeps
  the first candidate (BL-20261109-0331-loop-selection-protocol-2-design, decision 1).
  - So a sample `a` that submits is always the loop's deliverable. A submitted draft
    "passes every critical check and has every deliverable" (question (c) of that
    entry).
  - "Under rule 2 a repair can change the outcome only when the selected draft did not
    submit" (docs/experiments/README.md, "Registry row").
- **What that does to the hypothesis.** Review-2 can deliver anything but its own sample
  `a` only in a loop whose sample `a` does not submit.
- **Background, not a prediction.** In Phase 2 blind proxy graders graded the local
  model's six document-review runs. They accepted 3 of 3 on one seed and 1 of 3 on the
  other, and none is rowed `incomplete`.
  - The sources are BL-20261019-0432-phase2-result-provisional and the registry rows
    `p2-d1-…`, `p2-d2-…` and `p2-d3-…`.
  - Those runs used the earlier local model and other files.

E6 makes no claim about real documents, the desktop app or any cloud route.

## Decision rule

**The acceptance rule for one run.**
- **Decided (owner, 2026-11-17):** When does a run count as accepted?
  *Accepted as proposed:* the rule below. (Item 4.)
  - **Accepted:** the delivered review submitted, and the blind proxy grader accepted it.
    A review-2 run's delivered review is its loop's final candidate.
  - **Rejected:** it submitted and the grader rejected it.
  - **Not submitted, or stopped at a cap:** counted as rejected in every E6 count, as the
    review counts such a run (section 2.2, criterion 8; section 5.6, E3's rule). Its
    row's `outcome` is `incomplete`, as Phase 2 rowed such runs.
  - **`infra_invalid`:** a run that ended on infrastructure, by the `runClass` the row
    writer computes from the run's record. One re-run may replace it (see "Stop rule").
    Without one it counts as not accepted (docs/experiments/README.md, `runClass`).
  - **A loop with no selection** delivers nothing and counts as not accepted. The row
    writer never rows it `accepted` (docs/experiments/README.md, `runClass`). Its row is
    `infra_invalid` when the stop's class is infrastructure, and `incomplete` otherwise.
  - **The planted-defect count decides no acceptance.** It goes in `criticalChecks`.
    Reasons: "'7/7 automated checks' is never reported as accepted" (review section 2.5,
    item 5), and "Mechanics are never acceptance" (section 5.1, rule 9).

**Grading.** Blind proxy grades, provisional: the adopted default of review decision 11
(PLAN.md D9).
- **Decided (owner, 2026-11-17):** What is the blind-grading procedure, and who grades
  (issue #54, item 3)? *Accepted as proposed:* Phase 2's procedure, adapted as below
  (BL-20261013-1630-phase2-blind-bundles; BL-20261013-1650-phase2-grading-package).
  The counts follow item 3. (Item 5.)
  - **Bundles.** After the last run, `scripts/phase2-blind.py` builds two bundles a
    file, each under its own bundle and key roots. The tool names a bundle by job id and
    refuses to overwrite one.
    - **The drafts' bundle** holds the two review-1 runs and samples `a` and `b` of each
      loop: at most six.
    - **The repairs' bundle** holds each loop's repair: at most two. The tool refuses a
      repair beside the draft it started from, because the two share files
      (scripts/phase2-blind.py; tests/unit/phase2-blind.test.ts).
  - **As Phase 2's package did** (BL-20261013-1650-phase2-grading-package): the brief is
    copied into each bundle, and every file and directory is set to one timestamp.
  - **No source file** (*the draft's adaptation*). Phase 2's delegated graders also saw
    the task's inputs (BL-20261019-0410-blind-bundle-omissions). E6's graders get the
    brief and the bundle only, as "Inputs and exposure" states.
  - **Every candidate, not only the delivered one.** Question (d)'s default asks for
    both candidates of a repaired loop whose stage-1 draft submitted. Grading sample `b`
    too is the draft's addition.
  - **Graders.** A separate grading session runs two independent agents a file, one for
    each bundle. Neither sees the other bundle, so no grader can pair a repair with its
    draft. A grader holds no gold, key, arm or run record.
  - **The verdict.** Accept means "usable as delivered, or with at most 10 minutes of
    edits", Phase 2's wording. Each verdict carries the minutes, one line of reason and a
    guess.
  - **The guess** (*the draft's adaptation*). Phase 2's graders guessed the arm:
    `local`, `cloud` or `unsure`. E6's arms run the same write phase, so the guess is
    "single sample, repair or unsure". Review section 5.1, rule 3, asks for arm guesses,
    and they have no closer form here.
  - **One decoy in the batch,** not counted for any arm, as in Phase 2. The grading
    session plants it in a copy of one candidate and does not print the label mapping.
    In Phase 2 the harness author did both (BL-20261013-1630-phase2-blind-bundles).
  - **Before unblinding.** The verdict sheets' sha256 values are recorded before any key
    is opened and before the scorer runs.
  - **Weakly blinded.** A result with at least 80% correct guesses carries that label.
    The level is E3's, for arm guesses (review section 5.6); its use on this guess is
    the draft's.
    - Each bundle holds one kind of candidate. So the guess tests whether a grader can
      tell a bundle's kind, not one candidate from its neighbour.
  - **The record.** Rows carry `verdictBy` `agent_diagnostic`, the value Phase 2's proxy
    grades carry. `verdictBy` and second verdicts were open parts of decision 11 (issue
    #53; decision 3 of BL-20261115-1937-owner-adopts-standing-defaults).
    BL-20261117-0941-group-a-decided-under-delegation decides them, and this card does not restate that decision.
    - By that entry, an owner's verdict goes in a `--supersedes` row,
      which is all the row writer offers today.
  - **No owner sample is required.** Decision 11 names E5's jobs and a sample of E3 and
    E4, not E6.

**The questions, stated before the runs.** They are *accepted as proposed*, under
item 6, and their counts follow item 3.
1. **Accepts by arm.** Of each arm's six delivered reviews, how many are accepted?
2. **Planted defects by arm.** How many planted defects does each delivered review
   address?
3. **The loop's effect.** In how many of the six loops is the final candidate not sample
   `a`, and at which step? A loop that ends at `no_draft`, `critique_failed` or
   `repair_failed` is counted apart.
4. **The repair against its draft.** In each loop with a finished repair, does the
   repair address more planted defects than the draft it repaired, and does its grade
   differ?
5. **Harm.** How many control clauses did each candidate change, by the scorer's rule,
   and how many of its edits carry a C1 code?
6. **Single samples.** Over the 18 runs of the single write phase, how many are
   accepted, and how many defects does each address? Those are the six review-1 runs
   and the twelve samples `a` and `b`.

**How the answers are read.**
- **Decided (owner, 2026-11-17):** Which questions and tests read the counts, and what
  turns them into the route? *Accepted as proposed:* the questions above and the reading
  below, which follows the E0 card's Amendment 4, item 5. (Item 6.)
- **No pass level is set.** No source sets one for E6. Each answer is given as counts.
- **Question 1** is tested with Fisher's exact test on the two arms' accept counts. A
  difference is called shown only at a two-sided p below 0.05.
  - With six runs an arm, a difference of four or fewer is never shown.
  - Only 5 against 0, 6 against 1 and 6 against 0 are shown (p = 0.015, 0.015 and
    0.002). 6 against 2 gives p = 0.061.
- **Question 2** is tested with an exact permutation test on the per-run counts. The
  statistic is the sum of review-2's counts minus the sum of review-1's. The arm labels
  are exchanged within each file, which gives 216 arrangements. The two-sided p is the
  share whose statistic is at least as far from zero as the observed one.
  - The smallest p it can give is 0.009: in every file, both review-2 runs address more
    than both review-1 runs.
  - The same lead in two files, with all four counts of the third equal, gives p = 0.056
    and is not shown.
  - Defects are not pooled into one count per arm. Defects in one review share a run and
    a file, so they are not independent.
- **Question 4** is tested with an exact two-sided sign test over the loops whose two
  counts differ. It shows a difference only when all six loops differ the same way (p =
  0.031). Five of five gives p = 0.0625. The grades are reported as pairs, with no test.
  - A loop with no repair has no pair and is left out of the test. With fewer than six
    pairs the test can show nothing.
- **Questions 3, 5 and 6** are reported as counts. No difference in them is called
  shown.
- **Anything else is "no difference shown",** whichever arm the counts favour. That is
  not a finding that the arms are alike.
- **The three tests are not corrected for one another.**
- **A comparison chosen after the counts are seen** is labelled post hoc, as decision 4
  of BL-20261116-1546-e0-structured-fixtures-result labelled its own.

**What this size can and cannot show.**
- **If review-1 is accepted two or more times of six, no result shows review-2 better.**
  Six of six against two gives p = 0.061. Phase 2's local reviews were accepted 4 of 6
  times, on the earlier model.
- **When sample `a` submits, review-2 delivers that sample.** In those loops, questions
  1 and 2 compare two single samples. A difference there is variation between samples,
  not an effect of selection or repair.
- **So the arms can differ by design only where a sample `a` does not submit.** Question
  3 counts those loops.
- **Question 4 is the measurement the tie rule lacks.** It is paired on the identical
  draft. It needs all six loops to agree before it shows anything.
- **Two graders a file.** A repair and its draft go to different graders. So question
  4's grade pairs mix a difference between graders with the repair's effect. Question 1
  has the same mix wherever a loop delivers its repair.
- **A planted-defect count shows** that an edit sits on a planted defect and, where the
  gold gives a condition, that the clean copy meets it.
- **It does not show** whether a comment says the right thing, whether the other edits
  are right, what the review missed beyond the plants, or whether an owner would accept
  it.
- **Three files by one author, two graders a file, one endpoint, one model.** A result
  is about these files.

**What E6 changes** (review row E6: the desktop review route). *Accepted as proposed,*
under item 6:
- **If question 1 shows review-2 better:** review-2 is proposed as the route that
  backlog item 13 wires for document review. The owner records the choice.
- **If it shows review-1 better, or shows no difference:** the route stays the single
  sample. That is the route the driver applies today, and a loop costs three runs and a
  critique for one deliverable. The result entry says "no difference shown", not that
  the arms are alike.
- **Questions 3 to 6 change no rule here.** They may ground a later card on the
  selection rule or on skipping the repair. Either is "a later lever under its own
  entry" (question (c) of BL-20261109-0331-loop-selection-protocol-2-design).
- **The host flags ship either way** (review row E6).
- **The alternative, which was not chosen.** The review's frontier rule (section
  2.1, still proposed) calls a route better on quality when its accepts exceed the
  other's by more than one in six. Both arms are equal on fee and disclosed bytes. That
  rule would adopt review-2 at two more accepts of six, a difference the test above does
  not show.
- **Decided (owner, 2026-11-17):** Does E6 run with these arms and at the review's
  size, given review section 5.1, rule 1? That rule admits an experiment only if its
  pre-registered result changes a pending product decision. *Accepted as proposed:* yes,
  as the review sizes it: 12 runs in 4 days. Questions 3, 4 and 6 are worth having at
  that size, and a larger batch or another arm can be a later card. (Item 13.)
  - **Why the rule is in doubt.** Under protocol 2 review-2 delivers sample `a` whenever
    it submits, and all six of Phase 2's local review runs submitted.
  - Question 1 may then compare two single samples in every loop. No result would then
    show an effect of selection or repair.

## Stop rule

- **Decided (owner, 2026-11-17):** When does the batch stop? *Accepted as proposed:*
  the rules below. (Item 11.)
- **Stop before any request** if:
  - the doctor does not report ready;
  - the tracked tree is dirty, or the commit is not on `main`;
  - the manifest is not pinned on `main`, or a task's job or brief hash differs from it;
  - the Docker-gated document-review suite is not recorded `Verified` (item 9);
  - the doctor's report of the serving card differs from the state recorded for the
    batch before the first run (item 8).
- **How a run is read before its row exists.** Right after each run or loop, the session
  prints its row with `scripts/registry-row.py` and appends nothing. It reads
  `runClass`, `usd`, `cloudCalls` and `disclosedBytes` from that print. The rules below
  use those values.
  - The writer needs an `--outcome`, so the print carries a placeholder. Where the
    writer refuses the placeholder, its message names the run's class.
- **Stop the batch and record it** if:
  - any run's printed row shows a fee, a cloud call or a disclosed byte. E6 is local
    only;
  - a merge changes the source freeze before the last run. Runs do not span it, and the
    owner decides whether the batch restarts;
  - two runs in a row end `infra_invalid`. The cause is found before the next run,
    within half a day (PLAN.md section 4, the trial-first rule);
  - the running session opens a gold file. The files it exposed are then calibration
    only (review section 5.1, rule 3);
  - the four days end. What ran is recorded, and more time is the owner's call.
- **Re-runs.** A run or loop is run again only after an `infra_invalid` end, once, and
  never because of a result. Every run keeps its row and its directory.
  - A loop resumes a stage that ended on infrastructure once, at zero fee, by its own
    rule (BL-20261113-0836-infra-resume-design). That resume is not a second loop.
- **No early look.** No run is added, dropped or reordered because of a grade or a
  count. The scorer runs once, after the grades are filed.
