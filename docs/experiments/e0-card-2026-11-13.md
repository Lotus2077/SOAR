# E0 card: new-endpoint qualification and role calibration

Status: **proposed**. The items marked **Owner:** wait for the owner's answer. Every other
item carries the default its source states, or this card's own proposal where it says so.
This card is the pre-registration that docs/PROJECT_REVIEW_2026-11-05.md section 5.6
(row E0) and docs/HANDOFF.md "Start here" section 5, step 2 require. It resolves issue
#47 once the owner's answers are recorded. The run itself is issue #57. Its build-log
entry is BL-20261113-0728-e0-card.

The card records the served model's alias, engine version and context, never the
endpoint's address.

## Hypothesis

The endpoint the owner now serves can carry SOAR's local volume work at zero fee. A
single probe run, plus the role fixtures, re-derives every stage bound and clock and
settles five things:
- a thinking policy for each role;
- whether structured output is usable for each role;
- the adapter path;
- K, the number of concurrent streams;
- whether the figures qualified on 2026-11-04 still apply.

E0 makes no claim about product quality.

## Arms and tasks

**Probes** (`scripts/serving-probe.py`, probe version 2):
- **P1 to P9**, the existing probes. P1 reads the served alias, the model root basename,
  the context and the engine version.
- **P10**, structured output for each role: `response_format` `json_schema` from
  `pnpm probe:export-schemas`, 20 calls per role and thinking mode, thinking on and off.
  Truncation is counted apart from schema rejection.
- **P11**: prefill and decode at 20k, 60k and 120k tokens, cache reuse on the extraction
  layout, and K streams at 1, 2, 4 and 8.
- **The adapter probe**: `/openapi.json`, `/tokenize` parity, the reasoning field, and
  whether the legacy shape or `flash_next_v1` is consistent.

**Order:**
- First, run `python3 scripts/serving-probe.py --only P1` and check its output by hand
  (stop rule below).
- Then run P1, P10, P11 and the adapter probe in **one invocation**, after
  `pnpm probe:export-schemas` and before `pnpm probe:assess`.
- A serving card covers exactly one probe run. Refreshing any of its evidence means
  re-running all four and adopting a new card.

**Role fixtures:**
- **Planner** (`pnpm fixture:planner`): 3 conditions × 10 repeats on the exposed r3 index
  pinned in `docs/experiments/e0-planner-fixture-v1.json`. Raw replies are retained.
- **Extractor**: 3 synthetic chunks.
- **Judge**: a fixed claim set labelled by a separate session, scored against the
  agreement level in item 2 below. It runs only once that labelled set exists.
- No script runs the extractor or judge fixture yet. `scripts/` has only
  `planner-fixture.ts`, and `package.json` only `fixture:planner`. The command for each
  is named in an amendment to this card before that fixture runs, and nothing outside
  that amendment changes.

**Preconditions:**
- The run starts from a checkout of `main` that contains 7b.1 (#69) and 7a.1 (#76), so
  P11 measures the new extraction layout. `main` at 9d10b9a satisfies this.
- No pull request that changes `researchProtocolSha256()` merges between the export and
  `pnpm probe:assess`.

## The five items of issue #47

1. **Is the endpoint's model the one qualified on 2026-11-04?** (Decision 1, review
   section 5.10.)
   - **Owner:** confirm it, or say it is not confirmed.
   - If you confirm it and probe P1 matches, E0 is a delta check and the 2026-11-04
     figures stay admissible.
   - Default without confirmation: none of the 2026-11-04 figures apply, and E0
     re-derives every bound. This does not hold E0: the card may be committed with your
     entry owed (issue #47).
   - Probe P1 reads the served alias, model root basename, context and engine version.
     The writer's `--compare-*` rows show whether each is consistent with 2026-11-04.
   - P1 can show a difference, but it cannot prove identical weights (review section
     5.10). The reader's identity check later compares only the alias and, under
     `flash_next_v1`, the context.
2. **The judge fixture's per-claim agreement level.**
   - **Owner:** set the level, for example a share of claims on which the judge must
     agree with the labels.
   - The claim set is labelled by a separate session (review row E0) before the judge
     fixture runs. Who runs that session, and when, is yours to name with the level.
   - Default until both exist: the judge fixture does not run and the judge stays
     evidence-only.
3. **P10's 95% rule binds the strict variant** (`strict: true`, the default of
   `--p10-strict`).
   - If the server refuses strict and accepts non-strict, the probe falls back to
     non-strict, and no structured output is proposed.
   - Source: BL-20261108-1459-serving-card-reader-design, decision (9) ("Owner defaults
     recorded here"): strict by default, the probe's default.
4. **The planner fixture.**
   - Conditions `legacy-thinking`, `flash-thinking` and `thinking-off`, with 10 repeats
     each and an extraction call budget of 40, as the manifest proposes.
   - **Owner:** pin the exposed r3 index. Fill `indexSha256`, `briefSha256`,
     `sourceIdsSha256`, `sourceCount` and `mandatorySourceChunks` from the r3 run under
     the ignored `.soar/`, and set `status` to `pinned`. The fixture refuses a template
     or a mismatch before any request.
   - **Owner (this card proposes "retain"):** reasoning text is kept for synthetic and
     public inputs.
     - P10 runs without `--strip-reasoning`.
     - The planner fixture keeps its raw replies; it has no strip option.
     - Why: the review's row E0 retains raw replies, and its stop list (section 5.8)
       stops "discarding raw replies on public and synthetic runs".
     - Say "strip" to run P10 with `--strip-reasoning`. Stripping the fixture's replies
       would need a code change first.
5. **P11's K-stream range and prefill sizes**: K in {1, 2, 4, 8} and prefill at 20k, 60k
   and 120k tokens, as the script runs them.

## Defaults applied here

- **E1 does not gate E0.** This is the proposed default of an open owner question in
  BL-20261109-0351-e1-recoverability-card, decision (7). E0's probes and planner fixture
  use no broker or session, and E1 gates agent-runtime runs: E2 to E6 and loops.
- **How measurements become card values.** The writer's built-in proposals
  (`scripts/serving-card.py`, BL-20261108-1459-serving-card-reader-design decision (2)):
  - caps and thinking as the role export sent them;
  - structured output for each role by the 95% rule;
  - K = 1;
  - admission basis `none`.

  The writer marks the card `proposed`. Until 7a.2 (caps and thinking), 9 (structured
  output), 8.2b (K) and 7b.3 (admission) merge, the reader refuses an adopted card with
  any of those values off today's default.
- **Structured output is proposed by the 95% rule.** This is the proposed default of an
  open owner question in BL-20261108-1459-serving-card-reader-design, applied by the
  code.
  - The reader refuses such a non-default card until item 9 merges.
  - Until then, leave `SOAR_SERVING_CARD_FILE` and `SOAR_SERVING_CARD_SHA256` unset, or
    adopt an all-default card.
- **P10 is not aligned with the pipeline's requests.**
  - P10's thinking-off cells use the probe's own sampling settings, do not stream and
    omit `preserve_thinking`.
  - P10's synthesis off cell sends the thinking ceiling's `lengthCap` (1,200 words), so
    it never measures a thinking-off synthesis request
    (BL-20261109-0334-research-request-shapes-design).
  - So a passing P10 cell does not show that the pipeline's own requests are at least
    95% valid. This is a stated limit of E0's P10 result.
  - **Owner:** say "align" to have a P10-align pull request written first. E0's export
    then waits for it.

## Decision rule

E0 changes these decisions (review row E0, last column):
- **Stage bounds and clocks**: each is set from this run's measurements. Under a
  confirmed item 1 with a matching P1, the run is instead a delta check against
  2026-11-04.
- **Thinking policy for each role**: from P10, P11 and the planner fixture's three
  conditions.
- **Structured output for each role**: proposed only where P10's strict variant is at
  least 95% valid. That needs at least 20 calls, assessed under the protocol hash it
  sent, with the requested variant run and no unassessed reply.
- **The adapter path**: legacy or `flash_next_v1`, from the adapter probe.
- **K**:
  - P11 measures decode concurrency at K = 1, 2, 4 and 8 for a one-sentence prompt, not
    at extraction-size prompts.
  - The writer always proposes K = 1.
  - The reader refuses an adopted K above 1 until 8.2b merges. After that it accepts one
    only with a zero-error P11 burst at that K.
- **Whether the 2026-11-04 figures apply**: item 1 together with P1.
- **The judge threshold**: criterion 8's judge threshold applies in E3 and E4, and
  criterion 3's in E4, only if the judge fixture reaches item 2's level. Otherwise:
  - the judge stays evidence-only;
  - under the stop list, cloud claim verification is reconsidered.
- **Serving-recipe work** (section 5.8): it stays stopped unless E0 shows a role-level
  gap.

## Stop rule (proposed by this card)

- **Stop before any request** if:
  - the probe's zero-fee guard refuses. It refuses a base that is not loopback without
    `SOAR_VLLM_COST_POLICY=local_zero_cost`, and a non-loopback `http` base without
    `SOAR_ALLOW_INSECURE_VLLM_HTTP=true`;
  - the planner manifest is still a template, or does not match.
- **Stop after P1, and record the run as a negative result,** if the endpoint does not
  serve or `/v1/models` does not list the configured alias.
  - Run `python3 scripts/serving-probe.py --only P1` first and check its output by hand.
    The probe neither compares the alias nor stops after a failed probe.
  - Only then run P1, P10, P11 and the adapter probe in one invocation.
- **Discard the run and re-run P1, P10, P11 and the adapter probe together** if a pull
  request that changes `researchProtocolSha256()` merges between the export and
  `pnpm probe:assess`.
- **Before committing:**
  - the card writer refuses a served alias that looks like a file path;
  - check the written card for anything that looks like an address.
