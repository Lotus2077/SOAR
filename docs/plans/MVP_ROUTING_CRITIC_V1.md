# Compact cloud critique diagnostic

Status: Implementation approved under the owner's continuing routing experiment
goal. Paid dispatch remains gated on a frozen, independently reviewed implementation
and root-recorded approval. No new requests have been made for this diagnostic.

## Why this experiment

The original cloud-plan/local policy accepted four of six attempted patches for
USD 0.472680, versus six accepted cloud controls for USD 1.418164. Requiring an
unrestricted cloud review/repair phase subsequently failed both cost and observed
quality. Its three completed runs already cost USD 1.199436; only one was accepted.
One phase allowed many cloud requests and repeated substantial inspection and work.

Test whether one compact critique, followed only when needed by one bounded local
repair attempt, can recover the quality gap while retaining API savings. This is
a diagnostic on exposed artifacts, not an implemented end-to-end routing policy
or fresh evidence. All original failed results remain intact.

## Stage A: six one-response critiques

Use all six original cloud-plan/local candidate artifacts, in original task order.
Include their failures; do not select only the two known defects. Each model input
contains the public task, exact patch, complete changed/enclosing definitions,
deterministically selected public dependencies/tests, inventory and explicit
omissions. Selection uses source and task metadata only. Prior review verdicts,
evaluator gold, reference patches, hidden tests, fees and policy labels are excluded.

The serialized bundle is at most 96 KiB UTF-8. Required context that cannot fit
is an explicit preparation failure; do not silently truncate it or spend a request
claiming that complete review is possible. Optional omitted context is disclosed.
The complete canonical request, including prompts and JSON escaping, must fit
128,000 bytes. Freeze actual bytes and hashes before dispatch.

Use the same configured cloud model, medium reasoning, standard service tier,
explicit cache setting and 8,192-token output cap as the controls. Request plain
JSON with verdict `acceptable`, `repair_required` or `insufficient_context`, a
concise summary, at most eight source-bound actionable findings and explicit
missing context. Do not ask for private reasoning. There are no model tools,
command loop, second cloud call, format repair or automatic retry.

Validate complete response status, schema, paths and supplied line ranges. Settle
provider usage before semantic parsing: an invalid critique can still be billable.
A model verdict is guidance and never independent task acceptance.

## Accounting and dispatch boundary

Keep the original stage database and USD 150 aggregate ceiling. Preserve every
prior request, including the original unknown local request and USD 0.301480
unknown cloud reservation. A new unknown stops this diagnostic without a retry.

There are at most six paid requests, each with at most USD 0.70 reserved, and
USD 3 new total exposure, drawn from the remaining approved development allowance.
At the unchanged USD 4/20 per million input/output prices, the maximum admitted
request reservation is USD 0.675840. Before approval, the sum of all six exact
request reservations must fit the unchanged USD 3 total; the individual ceiling
does not authorize six maximum-sized requests. Keep the USD 24 fresh-confirmation reserve.
This is API accounting; owned hardware, electricity and utilization remain separate.

Reuse existing request admission and request-ledger settlement. New explicitly
labelled accounting-only carrier runs cannot complete or claim patch/check success.
They end with the fixed reason `diagnostic_only_no_patch_run_completion`; separate
candidate-bound receipts record critique success or failure. These carriers never
enter a patch-quality denominator. No original completed run is reopened.

Require frozen model/configuration/input/runtime identities, exact prior database
bindings, fresh provider metadata, and exclusive one-use batch/request claims.
Credentials remain solely in the existing trusted session and transient transport.
No new provider or private-source disclosure is introduced.

Before each new request, stop if known diagnostic fees exceed USD 0.661851. Even
six accepted final candidates would then miss the target: original P fees plus
new critique fees must remain below 80 percent of the six cloud controls' fees.
Check futility between requests; do not cancel an admitted request merely because
its expected cost makes advancement unlikely. Retain every attempted fee and every
unrun disposition. Do not resume this batch after a stop.

## Stage B: bounded local repair and independent acceptance

Only after Stage A responses are frozen, compare them offline with existing
independent review. An `acceptable` verdict on a materially regressed artifact,
an invalid response, missing required context or cost failure disqualifies the
candidate. Do not tune the critic against these outcomes and call a rerun fresh.

For `repair_required`, allow one native local repair attempt with at most eight
requests, including two finishing calls, in the existing isolated execution
environment. Preserve the original patch as its starting source. There is no
second critic, paid recovery or automatic retry. The concrete repair runner and
its source/patch/check bindings must be implemented and reviewed before execution;
Stage A authorization alone does not assert that these mechanics exist.

Evaluate all six final candidates with the independent checks and two blind
full-patch reviews per artifact. Retain failed/unsubmitted repairs, unknowns and
all fees. Require six accepted candidates, no additional paired material regression
and at least 20 percent lower combined API cost per acceptable patch. This can
qualify a candidate for fresh confirmation, but cannot prove end-to-end savings
or latency because the original patch generation is being reused.

## Return to the actual product goal

If the diagnostic qualifies, integrate the exact policy into the app's admitted
runtime, preserving the budget, check freshness and artifact semantics. Freeze
that complete implementation before attempting the four prepared fresh tasks
paired with cloud. Require no fewer accepted tasks than cloud, no extra paired
material regression, at least 20 percent lower API cost per acceptable patch and
at most 25 percent median slowdown. Count generation, critique, repairs and failures.

A four-task confirmation is limited MVP evidence, not population-level equivalence
or device payback. A failing diagnostic or confirmation does not finish the goal;
use its measured failure to choose the next policy or workload experiment.
