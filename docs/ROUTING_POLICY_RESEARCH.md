# Routing and collaboration policies for SOAR — 2026-09-08

Recommendation: add an observable checkpoint to the verified isolated native coding adapter, then compare **local-first with explicit escalation** and **cloud planning followed by local implementation** against local-only/cloud-only. Minions provides useful collaboration patterns. PyroDash provides a learned handoff idea and now substantive coding adapter code, but no public Qwen3.8 agentic offload checkpoint was found. Neither project's headline savings certify SOAR's workload.

The separate [118-request local study](LOCAL_CAPABILITY_DIAGNOSIS.md) found useful source-provided coding and a thinking-budget tradeoff, alongside specification errors and repeated XML contamination in text-command execution. Native inventory calls serialized correctly in three first-turn probes. The subsequent [native coding calibration](NATIVE_LOCAL_CALIBRATION.md) now verifies multi-turn execution: 60 valid native requests and two of four exposed tasks submitted and independently accepted. The other two tasks expose repeated actions without applying feedback and unfinished regression tests. The interface gate is cleared for this isolated set; production admission and routing quality remain unverified. Add trusted exact visible checks, a finishing reserve and an observable progress checkpoint before the policy comparison below.

This is a read-only primary-source/code audit. No downloaded code, model weights, training, benchmark, or inference was run. Public code was cloned only for inspection; live SOAR source and original outcomes were unchanged. BUILD_LOG was read through the approved local capability study. Prior memory was a search lead, and is corrected below where current source changed.

Minions' original paper is [arXiv:2502.15964v1](https://arxiv.org/pdf/2502.15964), covering long-document finance, medical and scientific QA. It reports Minion's 30.4x remote-cost reduction with 87% of baseline performance, and MinionS' 5.7x reduction with 97.9%. These are relative benchmark performance and cloud-cost figures, not exact correctness parity or measured repository-to-patch economics. The paper leaves detailed empirical latency study to future work. Its core idea needs no collaboration-specific retraining, so existing Qwen and cloud models can test it.

PyroDash's [paper](https://arxiv.org/html/2607.20327v1) studies a trained local policy that emits a control token, transfers its partial reasoning once, and lets a frozen stronger model finish the request. Training learns token embeddings, offload SFT behavior and cost-aware GRPO. No return to the small model occurs within that request. Its main table is five math benchmarks; the paper does not supply a SWE-bench result. This is a learned generation-time decision, not a free external router that can simply be attached to untrained Qwen3.8.

## What each policy actually decides

| Policy | Decision unit and controller | What local contributes | Practical SOAR fit |
|---|---|---|---|
| Current SOAR fixed scout | User/config selects the whole workflow; read-only local phase always precedes cloud | Host-observed excerpts only | Baseline implementation; it did not test dynamic routing or local coding |
| Request routing, e.g. RouteLLM | An external scorer selects strong/weak before answering a request | Entire answer when routed local | Useful later with matched-model labels; generic chat routers do not know repository state/progress |
| Cheap-first cascade, inspired by FrugalGPT | Try local, evaluate permitted signals, then either stop or escalate | Candidate patch plus executed visible checks | Best simple next policy; local successes can eliminate cloud calls |
| Minion | Cloud supervisor iteratively asks local questions; local owns full context | Answers/analysis grounded in context | Useful for uncertain investigations; cloud round trips remain mandatory |
| MinionS | Cloud decomposes into short jobs, local processes chunks, cloud aggregates | Filtered structured findings, not just raw excerpts | Best for large-context evidence tasks; parallelism advantage must be remeasured under concurrency one |
| MinionCode | Cloud creates runbook/tests; local implements; cloud reviews and requests edits | Actual code changes and test execution | Strong next collaboration candidate if local solves bounded edits but struggles with task planning |
| PyroDash | The trained local generator emits an offload directive during a model turn | Partial reasoning before strong completion | Research arm when compatible weights and training recipe exist; prompt-based escalation is a different, testable policy |

The policies may be combined, but testing a combination first would obscure which component helped. Model selection, thinking-budget selection, tool selection, whole-session escalation and phase assignment are distinct decisions. Speculative decoding is also different: it requires target verification of drafts and is chiefly a serving acceleration technique, not a means for local successes to avoid paid cloud generation.

## Minions: released implementation and adaptation limits

The core [Minion loop](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/minion.py) lets cloud send instructions to a local worker with context, then uses local responses in subsequent cloud turns. [MinionS](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/minions.py#L244) implements cloud-produced job preparation, local batch calls, structured answers/citations/explanations, filtering and synthesis. It supports code-aware chunking. This differs materially from SOAR forwarding only three short read/search excerpts and discarding generated local analysis.

The repository now also contains [MinionCode](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/minion_code.py#L124): cloud runbook, sequential local edits, predefined tests, cloud review and bounded edit attempts. A cloud review occurs after every attempt plus final review; this can consume more cloud output than a direct solver on short tasks. Local success cannot eliminate all cloud calls in this policy. No held-out coding-quality/cost proof for this module was established by the original document paper or this audit.

Borrow these policies, not the host runtime. MinionS runs generated preparation/transformation code using [Python exec](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/minions.py#L224). MinionCode's [WorkspaceManager](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/utils/workspace.py#L165) applies generated paths and runs test commands with shell=True in the host workspace. Its top-level success checks absence of an exception, although an unsuccessful development step only breaks the loop. Thus that field is not an acceptance result. SOAR should retain its existing isolated execution, immutable patches, accounting and independent evaluation.

[MinionArch](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/minion_arch.py#L185) really does route, but selects one local worker once from supplied capability descriptions; the cloud supervisor remains. Its [ArchRouter](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/minions/utils/arch_router.py#L59) loads katanemo/Arch-Router-1.5B. With only one owned local model this adds little selection value.

The [dependency bundle](https://github.com/HazyResearch/minions/blob/a87d0ee9063485ae2c065679c0471fd559aa5f4c/setup.py) includes many provider SDKs, UI, document, search, MCP and attestation packages; the README describes Python 3.10–3.11 testing. A generic OpenAI-compatible client exists, but its defaults/model-specific branches are not evidence of correct Qwen3.8 thinking/history handling or Sol's exact request constraints. A small policy implemented through SOAR's existing adapters is a smaller experiment than importing this entire stack.

## PyroDash: correction to earlier skepticism

The September 7 code-preview merge makes the earlier blanket statement that no collaboration engine/continuation semantics exist outdated. The current [coding adapter](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/evaluation/evaluation_code/adapter/server.py#L315) accepts Anthropic-style turns and calls a local OpenAI-compatible server. It detects `<|llm_offload|>N<|/llm_offload|>` in the reasoning portion, packages history and the partial trace, then makes one cloud request. The external mini-SWE agent performs tools and starts another model turn afterward: **one handoff per request is not one cloud call per coding episode**.

The [offload implementation](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/evaluation/evaluation_code/adapter/offload.py#L258) preserves normalized tool-call IDs/results, removes the offload instruction from cloud history, and places the partial trace in an assistant `<part_think>` message. This is prompted continuation through a stateless API, not transferred KV cache or guaranteed exact continuation. The adapter translates final native calls back to Anthropic tool_use; it does not execute them itself. Source also repairs a truncated directive ending in a digit and treats no closing think marker as inside thinking; these heuristics require adversarial protocol tests before import.

The advertised ten levels currently collapse to [three control buckets](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/evaluation/evaluation_code/adapter/offload.py#L155): zero disables thinking, 1–5 requests high, 6–9 requests max. The [HTTP client](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/evaluation/evaluation_code/adapter/openai_api.py#L58) sends max_tokens and vLLM chat_template_kwargs, ignores finish_reason, and returns errors as text. It is non-streaming internally; Anthropic SSE is rendered after inference. Outer response usage reports local counts while side statistics record both tiers, so an outer-client ledger alone would undercount cloud. This is not a drop-in replacement for SOAR's strict Sol adapter or unknown-exposure accounting.

The [math runner](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/evaluation/evaluation_math/math_eval.py#L85) uses raw completions with its trained tokenizer, stops at the special token and keeps it for detection. [Requirements](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/requirements.txt) include vLLM>=0.25.1, Torch 2.11.0, Transformers>=5.5.3, math verifiers, mini-SWE-agent and SWE-bench/Docker. These entry points are present; installation and matching experiment reproduction remain unverified here. No training implementation was present in the inspected repository tree.

The [public organization inventory](https://huggingface.co/pyromind/models), independently fetched through the public API during this audit, lists eleven models: only three are named PyroDash (SFT and GRPO lambda 0.05/0.6). Their [model card](https://huggingface.co/pyromind/PyroDash-4B-GRPO-Lambda-0.05) identifies Qwen3.5-4B ancestry, BF16, EasyHard-24K SFT, DAPO-Math-17k GRPO and frozen GLM-5.2-FP8. These are not Qwen3.8-27B FP8 weights. The lambda 0.05 math operating point reports 64.04% accuracy, 0.975 cloud calls and 95.34% cloud-token ratio; lambda 0.6 reports 54.55%, 0.012 calls and 1.90%. The low-cost setting should not be dismissed because the quality-oriented setting offloads nearly everything; neither establishes coding transfer.

The [current README](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/README_zh.md) names ScaleSWE/TMax for agentic SFT+OPD+GRPO and claims approximately 20% cost savings with roughly 5% lower accuracy. It now publishes an [aggregate coding Pareto figure](https://github.com/Pyromind-Dynamics/PyroDash/blob/4330d20561bec2c4c8aa9d2c46c1a9da77cfc397/docs/assets/fig_cost_accuracy_pareto_coding.png); its lambda 0.1 annotation instead shows 29% and four percentage points relative to DeepSeek-V4-Flash. I inspected the image. Public matching agentic weights, per-instance predictions/receipts and exact cost/configuration provenance were not located. The aggregate preview exists; its independent reproducibility remains unestablished.

## Adjacent approaches worth retaining

[RouteLLM](https://arxiv.org/abs/2406.18665) learns strong/weak selection from preference data and releases router models. Its [current controller](https://github.com/lm-sys/RouteLLM/blob/main/routellm/controller.py) routes from the last message's content and explicitly notes first-turn-only training. A repository tool observation is not the same input distribution. Its [matrix-factorization implementation](https://github.com/lm-sys/RouteLLM/blob/main/routellm/routers/matrix_factorization/model.py) calls OpenAI embeddings: router latency, fees and disclosure must be counted. Transfer results in its paper do not establish calibration for Qwen3.8/Sol coding. These ancillary source pages were inspected at main, not cloned/pinned in this audit.

[FrugalGPT](https://arxiv.org/abs/2305.05176) learns a model cascade and stopping thresholds using answer quality and cost. Its [released project](https://github.com/stanford-futuredata/FrugalGPT) includes cached-data examples. SOAR can test the simpler cheap-first principle using visible execution and bounded progress signals; that is not a reproduction of its trained scorer. Passing visible tests is not correctness certification, as SOAR's original independent review already demonstrated.

## A falsifiable next experiment

This is a proposal, not permission for new cloud calls. The bounded local-only studies are complete and native multi-turn execution is verified in isolation. Freeze the checkpoint policy, settings and handoff from calibration data before opening fresh held-out task outcomes.

Compare four same-task arms through SOAR's shared controller and sandbox: C cloud-only, L local-only, E local-first then one irreversible escalation to cloud at a defined checkpoint, and P one cloud plan followed by local execution with at most one cloud review/recovery phase. Keep the same total episode budget/deadline and tool permissions across arms. Use the same Qwen/Sol models and exact adapters; freeze request limits, phase caps and handoff schema. Start with a 12-task held-out screen stratified across simple edits, multi-file state and larger-context investigations; it can reject a policy, not prove general equivalence. Broader paired replication is required before a deployment-quality claim. Do not reuse original-screen acceptance tasks as unseen cases.

L, E and P are proposed coding policies, not values admitted by the current production policy and phase enums. Their implementation requires an explicit persisted transition and request-admission contract. E and P must reserve enough remaining time and budget at their checkpoint for the promised cloud phase. Use C as the primary savings and non-regression comparator; L establishes the local quality/cost frontier. With owner-attested zero local API fees, no positive-cost hybrid can beat L on API fees alone.

E's observable triggers should include an explicit structured request for help, a predeclared number of unsuccessful visible-test attempts, or repeated no-progress actions. A protocol/timeout/unknown-accounting failure remains a separate stop, not a difficulty label or automatic paid escalation. Handoffs should transfer a patch, changed-path hashes, executed commands/results and concise explicit findings. Do not depend on exposing internal reasoning. Freeze the router before hidden evaluation; final hidden tests and blind code review must never become route/stop signals.

A successful local submission and visible check yields a candidate for owner review; it does not automatically Keep or apply a patch. Preserve identical frozen visible checks across arms. Report independent evaluation acceptance separately from the owner's Keep/Reject decision. The original screen's false accepts show why a visible pass alone is insufficient.

P tests whether decomposition rescues local failures. E tests whether successful local work can avoid cloud entirely. Only add a MinionS-style long-context arm if source-reading cost or context degradation is an observed bottleneck; otherwise its mandatory planning/aggregation calls may add cost without saving much. A prompt-based ask-expert action on stock Qwen is a useful optional ablation, but must not be labeled PyroDash's trained offload policy.

Report all-assigned accepted patches, independent regression findings, total API cost per accepted patch, paired median/tail latency, local GPU/service time, unknown reserved cost, cloud request/round counts and handoff bytes. Audit necessary versus unnecessary escalation on paired outcomes and whether retained local artifacts actually reduce later cloud work. Separate input/cache/reasoning/output tokens; charge failed attempts and planner/reviewer/router calls. Keep the owner's device acquisition cost, utilization, lifetime and electricity as explicit measured values or sensitivities; local token fees alone are not all-in cost.

Pre-register a fail-fast screen rule: any material new regression or failure to lower cost per acceptable patch fails advancement; require a meaningful margin (for example 20% lower API cost) and a latency ceiling (for example no more than 25% median slowdown) before spending on a larger confirmation set. These are proposed product thresholds, not statistically established constants. If local succeeds but E fails, investigate gate/handoff loss. If P improves quality but costs more, price the improvement explicitly. If neither helps against C and L, stop adding routing complexity rather than training a router to hide the negative result.

## Measured offline handoff loss in the original peek task

The archived hybrid peek investigation retained six successful source reads totaling **43,758 bytes**, plus a separate 931-byte inventory. All six numbered outputs match offline reconstruction from public cachetools revision `4500e3d04288738d25acbb4973eb3c3e1bf41db9` byte for byte. They cover lines 1–719 of the 791-line module; line 120 repeats. No search, test-file read, or documentation-file read was recorded. Eight local requests settled, but the persisted v1 outcome was a generic fallback with **zero source-evidence bytes forwarded**. First H/D cloud input hashes matched, as reported in the original screen audit.

The partial-handoff repair changes when evidence may be forwarded; its excerpt helper is unchanged. An offline replay using canonical read-command headers retains **3,453 source-output bytes (7.89%)**, comprising 56 complete lines in ranges 360–379, 480–497, and 600–617, plus partial trailing text. Labels and truncation markers bring the summary to 3,784 bytes; the overall 4,096-byte cap is not binding. Even with no command headers, the last-three/1,200-byte-prefix rule can retain at most 3,600 source-output bytes (8.23%). Thus at least **91.77% of gathered output is excluded**, independently of unretained command whitespace.

The loss is task-relevant: the base cache, omitted-default sentinel pattern, `__missing__`, LFU/LRU access and touch methods, TTL's private recency mutation, and most TLRU expiration/access logic were gathered but disappear. TTL's item-access method survives, while its membership excerpt begins at an orphaned `except KeyError`, omitting the no-reordering lookup. The reconstructed summary is a counterfactual: v1 never supplied it, and the original exact exit status was not persisted. Eight requests and seven successful actions within 25.690 seconds strongly support step-limit exhaustion, but v2 eligibility additionally requires a settled provider outcome, no cancellation, and a valid deadline.

This establishes two separate integration failures: v1 discarded all gathered source, and the repaired selection rule still discards relevant definitions. It does not establish a downstream quality improvement from a different handoff. A later matched comparison must vary evidence selection while holding the solver configuration fixed. This offline audit made no provider calls or changes to original outcomes or runtime.
