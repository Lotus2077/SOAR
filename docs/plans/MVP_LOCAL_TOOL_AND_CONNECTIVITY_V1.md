# Small local execution and connectivity check

Status: Approved for one bounded execution by the owner's September 12 instruction
to take the next step and test internet access. This replaces no earlier failure
and grants no paid API allowance.

The immediate question is whether the owned local model can use short execution
commands and complete one useful deliverable. The earlier complex audit mixed
writing failures, public retrieval, task quality and evidence-contract overhead.

1. Three independent local calls each receive one small write/append operation.
   The host executes the returned command in the existing offline container and
   checks exact bytes, preserved input and actual program output. Each command is
   limited to 1,500 characters; each response to 4,096 tokens. No retries.
2. Separately, at most three local calls and one public HTTPS GET test direct API
   browsing exposure and the model's use of an unpredictable tool response. An
   offline-container DNS/TCP probe checks the execution container's restriction.
   None of these establishes the GPU server operating system's network access.
3. If all three writes pass with settled requests and unchanged source, run one
   fresh synthetic invoice audit with two inputs and one Markdown report. All
   inputs are already local. Limit: twenty model calls, thirty tool actions,
   fifteen minutes, no public phase, no extra evidence bundle. Preserve the
   candidate and use the frozen independent checker and a neutral source review.

The runtime adds specific feedback for invalid execute arguments at the output
limit, and stops after two consecutive such failures. Complete valid calls at the
limit remain executable. Unit tests must pass before source freeze. Runtime,
drivers, task metadata, image, endpoint identity and model are bound in a local
authority before dispatch; no task answers enter the solver.

Only authored synthetic inputs and the exact public connectivity response may
reach the existing owned endpoint. Zero declared API fees; no cloud fallback,
new deployment, real private inputs, or expansion of a failed run. Each process
has a bounded startup/work/cleanup allowance. Keep incomplete results and stop
dependent work on a failed prerequisite. Report hardware costs separately.

Acceptance is specific: exact write results, observed tool-mediated internet
access, and one independently accepted report. These do not prove general agent
quality, routing savings, four-family coverage, GPU-side browsing, or a released
MVP. The next product decision follows the observed result.
