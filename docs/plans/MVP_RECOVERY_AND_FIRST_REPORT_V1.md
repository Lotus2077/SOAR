milestone". This is a new allowance. Previous failed and unknown attempts remain
closed and are not replayed or relabeled.

The milestone has three concrete outcomes: the local agent recovers from the actual
append error, SOAR retrieves public content without relaxing destination checks,
and one synthetic invoice report passes its frozen independent evaluator and
neutral review. This is one development milestone, not a general-quality or release
claim.

1. Repair public retrieval. At most four small public DNS/TLS/DoH metadata probes
   may identify a usable resolver path. Preserve HTTPS verification, exact origin
   admission, rejection of non-public destination addresses, credential separation,
   bounded responses, deadlines and no redirects. Do not change OS/VPN settings.
   Any new resolver path must be explicitly host selected and covered by focused
   tests and independent review before live public content retrieval.
2. Test recovery using the existing runner. Start a new context with the original
   UTF-8 file, failed command and actual stderr. Supply the original requested
   append, with no corrected command. Limit: four model calls, six tool actions,
   three minutes, 4,096 output tokens, one attempt. The host checks exact final
   bytes and input preservation after a real finish and isolated verification.
3. On accepted recovery, run the still-sealed small invoice task once. Limit:
   twenty model calls, thirty tool actions, fifteen minutes, 4,096 output tokens.
   Inputs are local; web work cannot consume its budget or block its independent
   execution. Its one report must pass the already frozen five-gate checker and
   neutral source review. No extra evidence bundle is required.
4. Independently qualify the repaired web path with at most two model calls and
   one public GET: exact tool selection, a real response, and exact consumption
   of unpredictable response content. Keep a failed request instead of retrying it.
