# Two repair attempts with earlier check feedback

Date: 2026-09-10. Status: Proposed live dispatch; offline preparation is approved.
Live work requires the exact reviewed plan and root gate to be frozen first.

## Question and unchanged scope

Can the explicit earlier-check profile finish independently acceptable repairs on
both original exposed development seeds within the existing eight-call envelope?
This is a completion and quality go/no-go test. There is no concurrent control, so
it cannot establish that check timing caused an improvement or rank profiles.
The goal remains preserved quality and lower complete-session cost across the full
coding task mix, including work that requires cloud. No easy-task filter is inferred
from the six exposed development examples.

## Exact bounds

Run once in this order: `cache-repair-window` on the original cache-discard repair
seed, then `retry-repair-window` on the original Retry-After repair seed. Use only
the original public task, original compact critic and native host guidance. Keep
the original repositories, allowed paths and visible commands. Freeze both raw
objective hashes and their schema-normalized admitted hashes.

Each attempt uses disabled thinking, repair_window check scheduling, at most eight
model calls, 8192 output tokens per request including any reported reasoning,
256000 input bytes, 120 seconds per request and 600 seconds per episode. Keep the
same isolated pinned image, source handling and explicit checked submission.
The batch limit is two episodes, sixteen local requests, concurrency one and zero
new API fees. No cloud credential or provider is configured for this study.

Use a new ledger, storage and one-use claims. Do not recover or retry any historical
run. Unknown inference, cancellation, cleanup failure, evidence drift or evaluator
infrastructure failure stops further dispatch. Preserve both assigned dispositions,
including failed, claimed-without-run and unrun outcomes. A recovered patch is not
a submitted candidate. Report runtime elapsed time separately from offline artifact
composition and evaluation time. A zero-fee unknown outcome remains an unknown.

## Evaluation before promotion

Before inference, verify the runtime receipt, driver/evaluator source reviews and
tests, exact evaluation file bindings, and the deterministic known-probe wrappers
against original reference artifacts using the existing Docker evaluator. Retain
any reference/probe disagreement; do not change gold to fit a generated candidate.

The original-reference precheck failed one case on each task with verified harnesses
and cleanup. Those reference patches and negative receipts stay unchanged. Before
dispatch, independently reconcile the failures with the public requirements and
verify separately versioned corrected positive controls against both the original
oracles and the unchanged known probes. The corrected controls are evaluator-only:
they never replace the repair seeds, task objectives, critic messages or model input.

For each eligible submitted repair, verify exact admitted objective/run/profile,
source revision, source-bound passing checks, incremental patch and composition
against the original baseline. Run the original independent oracle and the frozen
known probes on that same composed patch, with matching receipt identities and
confirmed cleanup. Then independently review the full source change against the
public task. Mechanical checks alone never set semantic acceptance.

Both repairs must be accepted to advance. Rejoin all six original development
candidates with exact retained artifact identities and every planner, critic,
repair and fallback cost. Preserve the corrected cloud-control defects. Only a
complete development result that clears quality and economics justifies the four
untouched full-policy confirmation tasks. Those tasks are not part of this dispatch.

Confirmation must compare complete sessions with the same evaluation standard,
include all failures and unknown exposure, and target at least 20% lower API cost
per accepted patch, no additional material regression and at most 25% median latency
increase. These are MVP advancement thresholds, not a claim of universal parity.
Device payback and owner acceptance remain separate unverified requirements.
